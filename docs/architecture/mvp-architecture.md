# Career Companion: MVP Architecture & Known Limitations

This document describes the Sprint 4.5 MVP with the 2026-09-26 stabilization corrections, updated for the Sprint 6 status/evidence boundary (§9, 2026-10-02) automation submissions through MCP (§10, ADR-0002, 2026-10-02) the mail-first walkthrough (§11, 2026-10-11) and dev mode with sign-in by password (§12, 2026-10-12). See the [audit evidence and roadmap gates](../engineering/stabilization-audit.md) and backend [release/recovery guide](https://github.com/NitinSirsath/career-companion-backend/blob/main/STABILIZATION.md). Local verification does not establish live production readiness.

## 1. Authentication & Session Boundary
- **Implementation:** The primary authentication mechanism is Google OAuth via the `google-auth-library`. A user can also sign in with email and password (§12).
- **Session:** Authenticated sessions are managed securely using `express-session` with `connect-pg-simple`. Sessions are stored in the database (`cc_session` cookie).
- **Security:** All authenticated routes are strictly scoped to the `req.session.userId`.
- **Note:** Production startup rejects development authentication, weak/default signing secrets and non-HTTPS configured origins/redirects. The auth middleware independently refuses production header impersonation. Google email claims must be verified; an existing different Google identity cannot be silently replaced. Login rotates and persists the session. TLS-terminating deployments must configure the actual trusted proxy count.

## 2. Gmail Integration & Privacy
- **Metadata vs. Body:** The system stores sender, subject, message/thread IDs and timestamps. Snippets are transient classification inputs. The body is fetched on demand for Relevant or Uncertain mail and bounded to 8000 characters for extraction.
- **Privacy:** Raw email bodies are **never** persisted in the database and **never** logged. They leave the backend in two ways only: in memory to the user's AI provider for processing, and to the signed-in user when they open a mail on the Mails page (§11). That text is fetched from Gmail at that moment, sent to the user and dropped. No list, application or conversation endpoint returns body text. Gmail access tokens and refresh tokens are encrypted at rest using AES-256-GCM.
- **Sent mail:** During sync the user's own sent messages are noted only in conversations Career Companion already holds, and only as Gmail message ID, thread ID and sent time. No text, subject or recipient is stored. A sent message is never classified, matched or sent to AI. A reply the user writes in the app (§11) is handed to Gmail and dropped: its text is never stored or logged.
- **Token Refresh:** A shared OAuth client wrapper persists refreshed encrypted credentials conditionally; an old request cannot resurrect a disconnected connection. Authentication failures revoke the connection; quota-related 403 responses do not.
- **Sync Architecture:** `POST /api/gmail/sync` returns 202 after a durable queue handoff. A user-scoped database claim/lease excludes concurrent scans and allows stale-sync recovery. Initial sync captures history before scanning INBOX and Sent over the chosen lookback (1, 7, 14 or 30 days, default 1); after a gap the window grows to cover it, up to 30 days (`syncWindow`, `services/gmailSync.ts`); subsequent syncs consume history pages, falling back to full scan on expired history. Checkpoints advance only after ingestion/enqueueing succeeds. Stored messages are deduplicated; pending insert/enqueue gaps are recovered in bounded batches. The UI polls status and processing state.
- **Identity:** One mailbox is supported per user. Reconnecting that mailbox is allowed; changing mailbox identity is rejected until a separately designed migration exists.
- **Retention:** Raw bodies/snippets are not stored. Metadata, structured AI checkpoints and domain records persist until parent deletion. Disconnect clears tokens but retains existing domain data. A time-based retention/deletion policy remains a product decision.

## 3. AI Pipeline (User-Provided AI, ADR-0001)
- **Whose AI:** each user brings their own AI account from a curated, code-defined catalog: Google Gemini, OpenAI or Anthropic Claude. There is no Career Companion key and no automatic fallback. Each provider is offered only after it passes Career Companion's synthetic evaluation and its data-use text is approved ([provider evaluation](../ai/provider-evaluation.md)).
- **Provider-neutral contracts:** Career Companion owns the prompts and Zod schemas (`classification/v2`, `extraction/v2`). One adapter per API protocol translates them, and every result is validated with the same schema.
- **Cost boundary:**
  - Deterministic filtering precedes classification.
  - Each classification/extraction uses a unique `(emailId, operation, version)` ledger, a claim committed before the call (recording provider and model), and a validated completion checkpoint.
  - A **per-user** daily safety limit applies, and each model pauses on its own for each user. One user never affects another, and a busy model never stops another model.
  - SDK retries are disabled. Provider refusals never use attempts.
- **Uncertainty:** a crash or timeout around a provider call cannot prove whether it was charged. For per-email reads, a call with no answer in time uses 1 of 3 attempts and is tried again by itself; after the 3rd attempt it is held for the user's OK, and the user may approve exactly one more attempt ("Retry anyway") (owner decision, 2026-10-14). Batch triage: an uncertain batch is held and never resent automatically. Completed work is adopted; downstream matching failure does not replay AI.
- **Waiting:** without usable AI access, emails wait as `PENDING`. After a provider pause (rate limit, busy provider, no answer) they are read by themselves when the pause ends. "Read waiting mails now" sends one waiting mail first, as a test; the others follow only if it works. After a key, billing or model problem they resume when the user fixes access.

## 4. Deterministic Matching & State Inference
- **Matching:** The system deterministically matches processed emails to existing applications based on exact `companyName` string matches (after normalization).
- **Ambiguity:** If an email could belong to multiple applications (or if the company name cannot be securely matched), it enters an `AMBIGUOUS` state. The user manually resolves this on the frontend, enforcing human-in-the-loop accuracy.
- **State Inference:** State transitions (e.g., `APPLIED` → `INTERVIEW`) are strictly monotonic. The system will not automatically downgrade an application's state (e.g., moving from `OFFER` back to `ASSESSMENT`).
- **Integrity:** Email/application row locks serialize domain effects in one transaction. Database constraints reject duplicate email-derived events/actions and cross-owner links. Explicit user choices survive AI replay; ownership cannot be transferred implicitly.

## 5. Action & Follow-up Management
- Actions (e.g., "Schedule Interview", "Sign Offer") are created idempotently alongside `ApplicationEvent` records.
- Actions have explicit deadlines and statuses (`PENDING`, `COMPLETED`, `DISMISSED`) which the user can manage directly on the frontend.

## 6. Discord Notifications & Reliability
- **Why Discord Only?** Discord via webhooks is the easiest and most reliable notification channel for MVP, requiring no complex third-party API approval or app installation flow (unlike Slack or push notifications).
- **Delivery boundary:** A `NotificationDelivery` claim is committed before sending. Duplicate executions and uncertain successes do not automatically resend. Only explicit retryable rejections release the claim. This is not an exactly-once delivery guarantee.
- **Recipient boundary:** The global webhook is bound to `DISCORD_USER_ID`; delivery for every other owner is skipped. No multi-user notification configuration feature was added.
- **Known Limitation (Action → Queue Enqueue Window):** The system persists an Action to the PostgreSQL database inside a transaction, and *then* enqueues the notification job to `pg-boss`. If the process crashes immediately between DB persistence and `pg-boss` enqueueing, the notification will be lost. This lack of a transactional outbox is an accepted trade-off for the MVP to reduce architectural complexity.

## 7. Explicitly Deferred / Out of Scope for MVP
- Other Email providers (Outlook) or platforms (LinkedIn).
- Other Notification providers (Slack, WhatsApp, SMS).
- AI providers beyond the V1 catalog (Gemini, OpenAI, Claude); further OpenAI-compatible providers are catalog plus evaluation work (ADR-0001).
- Gmail Push Notifications (Pub/Sub) — Polling/sync is sufficient for V1.
- Redis/Kafka — PostgreSQL via `pg-boss` handles all queuing needs.
- Transactional Outbox pattern — Simple fire-and-forget job enqueueing is accepted for non-critical notifications.
- Microservices, event sourcing, or CQRS.
- Billing, teams, or enterprise SSO.

## 8. Reliability & Job Processing
- **Queueing:** `pg-boss` runs email processing, Gmail sync and Discord jobs directly in Postgres. Callers share an initialization promise. Queue singleton windows reduce duplicate jobs; database claims protect actual effects.
- **Retries:** Queue retries are bounded and delayed. AI attempts and each model's pause are durable, apart from the queue. Terminal errors are acknowledged without replay. A per-email AI call with no answer in time is tried again by itself, up to 3 tries in all, and then waits for the user's OK (owner decision, 2026-10-14). Only an uncertain batch is held and never sent again by itself. Exhausted work is not revived automatically: only the user's OK sends it again.
- **Pagination:** All public lists use the existing offset envelope, default/max 20, validated parameters, and stable ID tie-breakers. Sublists and application selectors are paginated. Details load by owned ID independently of list pages. Query invalidation, empty-page navigation and mutation errors are covered by UI tests; concurrent changes can still shift offset pages.

## 9. Application Status and Evidence Boundary (Sprint 6)
- **One read rule:** `ApplicationService` has a single response mapper used by create, list, detail and the status PATCH. It returns the stored `aiStatus`/`userStatus` plus derived `effectiveStatus` (`userStatus ?? aiStatus`), `statusSource` (`USER`/`AI`/`UNKNOWN`), `hasStatusConflict` and the stored `userStatusRevision`. Derived fields are not persisted.
- **One write path for manual state:** `PATCH /api/applications/:id/status` with a strict body `{ userStatus, expectedUserStatusRevision }`. One short transaction locks only the owned application row (`id` + authenticated `userId`), compares the revision before no-op detection, writes only manual fields and returns the canonical response from the same transaction. Errors: 400 `VALIDATION_ERROR`, 401, 404 `NOT_FOUND` (missing and foreign are identical), 409 `STATUS_CONFLICT`, sanitized 500. No email lock, external call, job, event, action or AI-ledger change. Matcher keeps email → application locking and writes only `aiStatus`.
- **Evidence selection:** events and each list/detail `recentEvent` add `recordedAt` and a bounded `sourceEmail` (`id`, `subject`, `sender`, `receivedAt`) selected with the page's query, never per event. Source ownership is checked in addition to the parent; a foreign source (only possible through inconsistent legacy data) is returned as null with its `emailId` nulled and a sanitized `evidence_ownership_mismatch` log. No body, snippet, extraction payload or prompt is returned, and reads never call Gmail or AI.
- **Runtime contracts:** the frontend parses create/list/detail/PATCH and events responses with the synchronized backend Zod schemas. Missing required keys or inconsistent derived fields are contract errors, never defaults. A newer client against an older backend shows a recoverable contract error.
- **Remaining limits:** no event occurrence time or agenda (email dates are unrestricted and may come from a Date header), no rematching/merging, no action source evidence (D1 deferred), no correction audit history, monotonic AI inference can still hold a wrong terminal AI state (manual correction is the remedy).

## 10. Automation Submissions through MCP (ADR-0002)
- **Boundary:** the backend hosts one Streamable HTTP MCP server at `POST /mcp` (`backend/src/mcp/`), a thin adapter over the domain service `services/externalSubmission.ts`. One write-only, idempotent tool, `record_application_submission`; no resources, prompts or read tools. The user's own automation agent is the client and pushes one call per confirmed submission. Career Companion never reads the laptop and never applies to jobs.
- **Middleware order:** `/mcp` is mounted before CORS, the global JSON parser, cookies and session. Per request: one log line → POST only (405) → `Host` allowlist (`MCP_ALLOWED_HOSTS`, 403) → `Origin` allowlist (`MCP_ALLOWED_ORIGINS`, default empty; no `Origin` passes) → Bearer integration token (401 with `WWW-Authenticate`) → 32 KB JSON (413/400 as JSON-RPC errors, no stack) → SDK handler.
- **SDK wiring:** `@modelcontextprotocol/server` 2.2.0 and `/node` 2.1.0, pinned. The Express add-on is not used because it re-types `req.auth` app-wide; the runtime-neutral helpers (`validateHostHeader`, `validateOriginHeader`, `verifyBearerToken`, `bearerAuthChallengeResponse`, `createMcpHandler`, `toNodeHandler`) are used directly, and the verified `AuthInfo` is passed to the SDK on a request view, so the session `req.auth` is never touched. Input is validated in the tool handler with the strict schema, so every failure is a tool error with code `invalid_input` and field names only.
- **Token auth:** per-user `ccmcp_` tokens (SHA-256 hashed, single scope, expiring, revocable) are accepted only on `/mcp`; sessions and the development header are never accepted there, and tokens never work on `/api`. The user always comes from the token.
- **Intake:** one transaction per call under `pg_advisory_xact_lock(namespace, hashtext(userId))`: ref check (repeat → `already_recorded`), daily cap (`MCP_DAILY_SUBMISSION_LIMIT`, default 500), insert, conservative match, create or link with the `AUTOMATION_SUBMITTED` event. User review (`/api/submissions/pending`, `/api/submissions/:id/resolve`) takes the same lock. No AI call, no queue, no new infrastructure.
- **Audit:** one `mcp_request` log line per request (token ID, user ID, method, tool, outcome, duration, whether a replay differed); no payload values and no token material.
- **Remaining limits:** until deployment the endpoint only works with Career Companion on the same machine as the agent; production needs edge routing for `/mcp` and `MCP_ALLOWED_HOSTS` set to the `Host` the backend receives. There is no per-IP rate limiter (deployment work). Antigravity compatibility is verified by the owner (MCP-09 part B).

## 11. Mail-first Walkthrough: Conversations and Live Gmail Reading (2026-10-11)
- **Why:** a new job mail used to give no value until the user created an application by hand and linked the mail. Now the mail itself shows what it needs, and the application is one click away.
- **Conversations:** `GET /api/conversations` lists job-related mail as one row per Gmail thread (`services/conversationQuery.ts`, one query). A row carries the newest subject and sender, what the AI read (type, company, role), the newest request with its state, the application if there is one, and a New mark that ends when the user opens the conversation (`emails.seenAt`). These reads use stored metadata and AI results only: no Gmail call, no AI call, no body text.
- **Request state:** derived on read, never stored as one field. `DONE` when the request's application action is completed or dismissed, or, while it has no action, when the user marked it done (`emails.requestUserState`). `REPLIED` when the user sent a message in the thread after the request arrived, unless they reopened it later. Otherwise `OPEN`. Marking done or reopening also completes or reopens the matching application action, so every page agrees. A reply alone does not complete the action; the application page shows that pending action as **Replied** too, with the reply time (`repliedAt` on the application's action list, same rule; owner decision, 2026-10-17).
- **Sent mail:** see §2. Later syncs take sent messages from the Gmail history feed; a full sync scans the sent mail of the sync window once. Both keep only messages in threads already held (`outgoing_emails`).
- **One-click application:** `POST /api/conversations/:key/application` creates the application from the company and role the AI read, or joins the one application of the user that fits. It links every waiting mail of the conversation with the normal match effects (timeline, status, actions), under the same per-user lock as matching, then runs the existing matcher over other waiting mail of the same company. Answers: 400 `COMPANY_REQUIRED` (the AI read no company; the client sends one), 409 `APPLICATION_CHOICE_REQUIRED` with the applications that fit (the client sends `applicationId`), 409 `CONVERSATION_LINKED`. No AI call is made. Gmail sync still never creates an application by itself: it always starts with the user's click.
- **Live Gmail reading:** `/api/mailbox` reads Gmail on request and stores nothing: the inbox list (20 threads a page, in Gmail's order, paged by Gmail's token), one thread with every message's text, labels and attachment names (drafts left out), and one attachment, always as a file download. Responses carry `Cache-Control: no-store`. Failures become answers the user can act on: 409 `GMAIL_NOT_CONNECTED`, 404 when the mail is gone, 502 `GMAIL_UNAVAILABLE`, 413 `ATTACHMENT_TOO_LARGE`. No archive, delete or label change.
- **Reply from the app:** `POST /api/mailbox/threads/:threadId/replies` (`{ replyId, text }`) sends a plain-text reply into the thread through `withGmail`, so prod and dev mode run the same code.
  - **Permission:** connecting Gmail asks for `gmail.readonly` and `gmail.send`. `gmail_connections.canSend` holds what Google granted, and `GET /api/gmail/status` reports it. A connection made for reading only answers 403 `GMAIL_SEND_NOT_ALLOWED` until the user connects again ("Allow sending"); `GET /api/gmail/connect?returnTo=` brings them back to the mail.
  - **Recipient:** worked out by the backend from the thread: the newest mail from someone else, its Reply-To when it has one. The request carries no address. Reading a thread reports it as `replyTo`.
  - **To everyone on the mail:** reading a thread also reports `replyCc`: the To and Cc addresses of that same mail, each once, without the user's own mailbox and without `replyTo`. A `+tag` and, at Gmail, dots before the @ still count as the user's own mailbox (`mailboxKey` in `contracts/mailbox.ts`). With `toAll: true` the reply goes to `replyTo` in To and to those people in Cc. Left out or `false`, it goes to `replyTo` alone, so an older page keeps working. The request names no address either way; the page shows both lists and offers the two choices.
  - **Sent once:** the page makes one `replyId` for each reply. It is written to `mail_replies` before the send call; the same ID is answered from that row and sends nothing. A clear refusal from Gmail frees the ID. No answer is 502 `MAIL_REPLY_UNCONFIRMED`, and the app never sends again by itself.
  - **Replied at once:** in a conversation the app holds, the sent message is noted in `outgoing_emails` right away.
  - **Not in it:** new mail, attachments, adding or removing single receivers, drafts and formatting. Plain text only.
- **Frontend:** the Mails page is the home page, with a Job mails tab and a Gmail tab; both open a mail details page. A sender's HTML is shown only inside a sandboxed frame whose content policy allows no script and no network request; pictures load after the user asks. Live mail leaves the browser's query cache when the page is left. The Dashboard and the Agenda are in the navigation and both show "Coming soon" (one shared page part, `components/ComingSoon.tsx`); the code of the earlier pages stays in the repository, shown nowhere.
- **New mails only:** the migration marks every existing email as seen and backfills nothing. No older mail is read again, classified again or matched again.
- **Remaining limits:** a reply written in Gmail itself shows as "Replied" after the next sync; a reply sent from the app shows at once. The same-company step after a link looks at the newest 1000 waiting mails. In dev mode the mail sandbox stands in for Gmail on these pages (§12). Tracking a missed mail from the Gmail tab, choosing an application by hand, dashboard analytics and AI reading of the user's own replies are later work (`[Later]` issues of COM-158).

## 12. Dev Mode, the Mail Sandbox and Sign-in by Password (2026-10-12)

How to use it: [Dev mode and the mail sandbox](../engineering/dev-mode.md).

- **One switch:** `APP_MODE` is `prod` (the default) or `dev`, read in `utils/config.ts` and checked again on every use. `dev` never starts with `NODE_ENV=production`, and only on a database whose name ends in `_dev`; prod mode refuses such a database. `GET /api/app-mode` (public) tells the frontend the mode, which has no setting of its own. `npm run devmode` makes `.env.dev`, creates and migrates the dev database and starts the backend. This replaces `TEST_TOOLS_ENABLED`, `VITE_TEST_TOOLS` and the test inbox.
- **Mail sandbox:** in dev mode each user has a sandbox mailbox (`sandbox_messages`) that stands in for their Gmail account. A message has the shape of a Gmail message: Gmail-style IDs, a history number, labels, headers, and the text as a plain part and an HTML part. `/api/sandbox` (404 before login in prod mode) sends a new mail to the user from any typed address, replies in a conversation as either side, lists Inbox and Sent, reads a conversation with what the app did with each mail, and resets the user's dev data.
- **Send, then sync:** sending writes only to the sandbox. `withGmail` hands callers a sandbox client in dev mode that answers the Gmail calls the app makes, so `gmailSync.ts`, the Gmail tab and the mail details page run unchanged, and a sandbox mail reaches the app only through sync. No Google client is built in dev mode. Gmail connect is one click with no Google screen.
- **Privacy:** the sandbox stores mail text, because it is the stand-in for Gmail. Only dev mode writes to it; in prod the table stays empty. The app's own tables keep to the rules of §2 in both modes: no body text is stored, and of the user's own mail only message ID, thread ID and sent time.
- **Real AI only:** nothing is ever filled in for the AI. With no AI key a synced mail waits and is reported as `AI_KEY_MISSING`.
- **Sign-in by password:** `POST /api/auth/login` starts the same session as Google sign-in. `POST /api/auth/password` sets the first password or changes it (the current one is then required, and the user's other sessions end). `POST /api/auth/register` exists in dev mode only: in prod a user is created by Google sign-in only, so every prod email is one Google confirmed. Passwords are 10 to 200 characters and stored only as salted scrypt hashes. Five wrong tries for one email in 15 minutes block that email, and 20 from one network address block that address, until the tries are 15 minutes old. A wrong email and a wrong password get the same answer. The app sends no email: a forgotten password is replaced after signing in with Google. In dev mode Google sign-in is off.
- **Remaining limits:** a received sandbox mail always arrives now, in Gmail's "Primary" category, with no attachment. Choosing the arrival time, attachments, search and an AI writer for test mail are later work (`[Later]` issues of the dev mode epic).
