## Verdict

**The architecture is suitable for incremental ingestion within its current scope. Keep it.** Gmail history paging, durable `lastHistoryId`, initial/reconciliation scans, owner-scoped uniqueness, leases, background ingestion, AI operation claims, and UI polling already exist. Sprint 5 needs live proof, targeted recovery corrections, a real local worker/browser smoke, and complete diagnostics. It does not need a new Gmail ingestion design.

Its scope is additive ingestion of recent INBOX mail and newly INBOX-labeled mail. It does not mirror all Gmail labels, deletions, archive state, read/unread state, or old mail. Existing stored rows are retained even when outside the current 90-day scope. A “full scan” means nondestructive reconciliation of that scope, never dropping/reimporting the dataset. There is no scheduler or Gmail push subscription in the inspected source; repeat sync is user-triggered.

No new table/index/migration is required by the default Sprint 5 proposal. ## Provider contract references

Google documents history-based partial sync and 404 when the stored anchor is outside available history. This supports retaining the existing nondestructive reconciliation path. [Gmail synchronization guide](https://developers.google.com/workspace/gmail/api/guides/sync).

History IDs are strings, increase with gaps, and pagination must be consumed before storing the terminal response checkpoint. Typed message/label additions are appropriate; duplicate message references need deduplication. [History API contract](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list).

401 can require token refresh; 403 reasons include quota and policy failures, so status alone cannot identify revoked authorization. Delayed bounded retries apply to transient failures. [Gmail error guidance](https://developers.google.com/workspace/gmail/api/guides/handle-errors).

These references were read for planning; they are not evidence that this application's live provider flow has passed.
