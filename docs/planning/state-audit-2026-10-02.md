# State audit — 2026-10-02 (before the move to the personal PC)

Status: **read-only audit record.** It is the evidence base for the [roadmap](README.md). No code or test was changed or run against a database. Typecheck and lint were run read-only (backend and frontend: 0 errors).

**Method.** Eight auditors read the current code and docs, one area each. Every gap they reported was then re-checked by an independent verifier told to refute it; high and critical claims got a second verifier judging scope and value. The tables keep the verifier's corrected statement, not the original claim. Line numbers are as of 2026-10-02 and will drift; each ticket re-states the references it relies on.

**Limits.** Static reading only. Test counts were counted, not run (backend 621 in 43 files, frontend 154 in 15 files, matching the reports). No migration lane, smoke or live provider call was run. Results claimed by earlier reports still need the [Phase 0](migration-verification/README.md) re-run.

**Verdict key.** C = confirmed, P = partly confirmed (the corrected statement says which part holds), R = refuted. Severity is the verifier's, which is often lower than the auditor's.


## MCPB — MCP backend

The MCP backend matches ADR-0002 and the plan's acceptance criteria item by item. MCP-01 to MCP-07 are done in code. MCP-09 part A is present in code; the execution report says it passed, but this read-only audit could not re-run it. The endpoint is mounted at src/index.ts:37, before CORS, JSON, cookies and session. It checks, in order: POST only (405), Host allowlist (403), Origin allowlist (403, requests without Origin pass), Bearer integration token (401 with WWW-Authenticate), then a 32 KB JSON limit. Errors are JSON with no stack trace. It is stateless (per-request McpServer on the SDK's createMcpHandler). It serves both the 2026-07-28 protocol and the 2025-era protocol through the stateless fallback. The SDK is pinned exactly (server 2.2.0, node 2.1.0), and the Express add-on is not used. Tokens are sound: 32 random bytes in base64url, only a SHA-256 hash is stored, the format is checked before any database lookup, there is one scope, expiry and revocation are checked on every request, lastUsedAt is updated, and the 5-active cap holds under an advisory lock. The plaintext is never stored, logged, or carried past verification. Intake runs as one transaction per call under pg_advisory_xact_lock(0x4d435001, hashtext(userId)). The order is: ref check, daily cap, match by the exact ADR section 7 matrix plus edge rules, then create or link with one AUTOMATION_SUBMITTED event. Every query is scoped by userId, and database triggers back up ownership. Intake has no side effects beyond creating or linking the application and adding the event: no actions, notifications, jobs or AI calls, and it never writes aiStatus or userStatus. deriveStatus and the Gmail matcher are byte-identical to the post-BYO-AI baseline. …

## AIB — BYO AI backend

The BYO AI backend is built and well structured, but it is not production-ready. No provider is certified, so production currently has no working AI path. In code, users bring their own keys. There is one provider seam (createProviderClient) and three protocol adapters (Gemini, OpenAI-compatible, Anthropic), all with SDK retries off, a fixed catalog base URL, per-model timeouts and sanitized ProviderFailure errors that carry no cause. Contracts are provider-neutral with pinned fingerprints, and the derived Gemini schema is test-proven equal to the old hand-written one. Keys are sealed with AES-256-GCM under a dedicated key, with AAD bound to the user ID. They are write-only, opened only in access.ts and settings.ts (boundary test), and an unreadable key becomes KEY_UNREADABLE. The settings API verifies before saving, keeps the old setup when a new key is rejected, needs a key and consent to switch provider, and the route plus service layer are session-scoped. The per-user safety limit (default 500), atomic conditional counters, capped cooldowns, the refusal rule (claim released, attempt restored), the revision guard, waiting as PENDING with the pg-boss cancel trick (proven against installed pg-boss 12.31, whose job_i4 index excludes cancelled jobs), and user-approved retry with a per-approval job key are all implemented and tested. Shared contracts (ai.ts, aiCatalog.ts) are byte-identical in backend and frontend. The main blocker: all three catalog providers are status 'hidden'. In production isOffered() is false for all of them, the hosted Gemini key is refused at startup, and no live provider call has ever been made. …
