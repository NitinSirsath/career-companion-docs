## 1. Title

Add concurrency-safe manual application status correction.

## 2. Sprint goal contribution

Let users set, change and clear their own status without a competing editor silently overwriting a newer manual decision.

## 3. Context

UF-09 in [user flows](../../product/user-flows.md) requires manual correction. The [domain model](../../domain/domain-model.md) already separates AI and user state, but no mutation is exposed. Revision and clear semantics below are proposed decisions for approval, not previously delivered behavior.

## 4. Current implementation

- `backend/prisma/schema.prisma`: Application has aiStatus, userStatus and userStatusSetAt; no manual revision.
- `backend/src/services/application.ts`, `src/routes/application.ts`, `src/contracts/application.ts`: owned reads and creation, no status PATCH.
- `backend/src/services/matcher.ts`: locks email then application and updates AI state independently.
- `backend/src/tests/application.test.ts`, `src/tests/matcher.test.ts`, `src/tests/ai-idempotency.test.ts`, `src/tests/stabilization-safety.test.ts`: existing focused test locations.
- `backend/src/utils/testDatabase.ts`: safety helper; direct Prisma CLI does not invoke it.
- `frontend/scripts/sync-contracts.mjs` and application test fixtures need coordinated additive contract updates.

## 5. Problem/gap

There is no supported correction path. A naïve last-write-wins PATCH would lose concurrent edits; updatedAt is unsuitable as a manual token because AI/background work also changes the application.

## 6. Proposed implementation

Add an owned service operation and `PATCH /api/applications/:id/status`. In one transaction, lock the application row using both id and authenticated userId, verify its manual revision, then apply a narrow change.

Compare `expectedUserStatusRevision` before testing for a no-op. A stale request returns 409 even if its requested value equals the latest value. With a current revision, identical userStatus returns 200 unchanged, preserving revision and confirmation timestamp. A changed non-null value sets userStatus, sets server-generated userStatusSetAt and increments revision once. Clearing sets both userStatus and userStatusSetAt to null and increments revision once. Ordinary updatedAt changes on a real write.

Return the full S6-01 response, including the new revision, from the same transaction snapshot. Reuse a transaction-aware mapper/query for enrichment rather than performing an unrelated later read that obscures the acknowledged revision. Do not lock emails or perform external calls. Application-only locking must remain compatible with matcher's email-then-application order.

AI updates must never modify userStatus, userStatusSetAt or userStatusRevision. Manual corrections must not create recruitment events, resolve actions, enqueue jobs, invoke providers or alter AI operation/budget records. Follow the domain distinction between latest correction provenance and recruitment history.

## 7. Architecture impact

Extend the current authenticated route/service/contract boundary. Database concurrency protects manual decisions across tabs/devices; frontend frozen revisions in S6-04 ensure that protection is actually used. No distributed lock, outbox or new worker.

## 8. Data model impact

Propose `Application.userStatusRevision Int @default(0)` with a new additive migration under the existing `backend/prisma/migrations/` directory. No migration file is created by this planning task. Existing rows receive zero; preserve stored statuses and timestamps exactly. A legacy non-null userStatus with null userStatusSetAt remains “confirmation time unknown”; do not invent dates.

No new table/index is needed for primary-key row locking. Fresh and upgrade tests must retain IDs, ownership constraints, existing AI operations, events and actions. Use the guard before any migration command, and regenerate Prisma before typecheck/build. Preserve data on rollback; no reset or destructive down migration.

## 9. API contracts

Strict request body, rejecting unknown fields:

```json
{
  "userStatus": "INTERVIEW",
  "expectedUserStatusRevision": 0
}
```

userStatus accepts APPLIED, RECRUITER_CONTACT, ASSESSMENT, INTERVIEW, OFFER, REJECTED, CLOSED or null. Revision is a nonnegative integer. Validate the path as UUID. Reject submitted userId, aiStatus, server timestamps and other undeclared fields.

Success 200 returns the full canonical ApplicationResponse; add required `userStatusRevision` to create/list/detail/mutation schemas. New applications return zero. Coordinate frontend fixtures and runtime parsing immediately.

| HTTP | Error code / meaning |
| --- | --- |
| 400 | VALIDATION_ERROR: invalid UUID/body/status/revision |
| 401 | UNAUTHORIZED: no valid session |
| 404 | NOT_FOUND: missing or foreign application, identical response |
| 409 | STATUS_CONFLICT: stale expected manual revision; refetch before deliberate retry |
| 500 | Sanitized existing internal-error envelope; client must consider the outcome uncertain |

Use the project's existing error envelope. A conflict need not disclose a snapshot in its body; the owned GET supplies current state. No automatic mutation retry.

## 10. Frontend impact

S6-04 supplies the editor. This ticket synchronizes required revision schemas and fixtures so intermediate commits remain coherent. The client must submit the revision captured when editing began; a background refetch must not replace that draft's revision. Missing revision blocks editing rather than defaulting to zero.

## 11. AI impact

None on provider abstraction, prompts, schemas, operation versions, budgets or retries. Existing aiStatus is retained even during a manual override; clearing reveals its current persisted value without a new AI call.

## 12. Background-job impact

None from correction. Test zero job enqueue operations, including notifications. Concurrent legitimate AI processing can proceed but must preserve all three manual fields. Drain unrelated fixture work before measuring correction side effects.

## 13. Security/privacy

Authenticate before selecting a row; scope the lock/write by owner. Never trust a body userId. Foreign and missing IDs use the same 404. Preserve existing credential/cookie protections and DB ownership triggers. Logs may contain approved correlation IDs and sanitized errors, not email content or credentials.

## 14. Testing

Cover all statuses, clear, repeated clear, same-value no-op, legacy null timestamp, strict payload validation and ownership. Two writes with the same revision must yield one successful change and one 409. Assert revision comparison precedes no-op detection. Interleave AI writes with manual set/clear and verify separation.

Simulate lost acknowledgement after commit: retrying the original stale revision returns 409 without another change. Verify rollback on transaction failure. Snapshot event/action/job/AI-ledger counts around a quiescent correction to prove no side effects. Test fresh schema and additive upgrade using synthetic legacy rows; compare fields before/after. Guard rejection must precede any migration invocation.

## 15. Acceptance criteria

- [ ] Owned set/change/clear works with the seven supported statuses and null.
- [ ] Concurrent edits use an atomic lock/revision check; stale requests always return 409.
- [ ] Current same-value requests preserve revision and timestamp; changes increment revision exactly once.
- [ ] AI writes preserve all manual fields and revision.
- [ ] Strict payload validation and identical foreign/missing 404 are tested.
- [ ] Correction makes zero provider calls, job enqueues, AI-ledger changes, events or action transitions.
- [ ] Required revision appears in every application response and synchronized fixture.
- [ ] Guarded fresh/upgrade checks preserve existing data and ownership constraints.
- [ ] Lost-response, rollback and legacy-timestamp behavior are documented and tested.

## 16. Non-goals

Full correction audit log, recruitment event synthesis, app merge/rematching, bulk corrections, action obsolescence, AI changes, historical replay and automatic notification.

## 17. Dependencies

Product approval of clear/latest-only provenance and revision semantics is needed when finalizing this proposal. S6-04 depends on this endpoint.

## 18. Failure/recovery behavior

Validation/auth/ownership/conflict rejection does not mutate. Transaction failure rolls back. A timeout, lost response or malformed 2xx can occur after commit: refetch the owned application and preserve the draft; never automatically resend with a fresh revision. If reconciliation fails, show “Save outcome unknown” and block save until current state is loaded. A 409 requires explicit user review and deliberate rebasing before another save.

Roll back UI capability by disabling editing while retaining canonical S6-01 reads and persisted corrections. Keep the additive column. Do not undo user decisions or restore AI-first display.

## 21. Engineering decision notes

A dedicated revision avoids false conflicts from AI writes and actual lost edits from last-write-wins. Revision comparison before no-op preserves stale-editor detection. A current no-op does not manufacture a new confirmation time. Application-only locking avoids an inverted lock order. Latest correction fields satisfy the scoped provenance requirement; a full audit table is deferred explicitly.
