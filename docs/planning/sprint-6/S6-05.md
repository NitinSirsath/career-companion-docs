## 1. Title

Verify the complete status workflow and publish its operating contract.

## 2. Sprint goal contribution

Prove that consistent status, correction, evidence and recovery work together without losing user choices, bypassing workers or spending AI budget for manual edits.

## 3. Context

Earlier tickets own focused tests. Integrated verification must build on completed Sprint 5 recovery and real worker/browser evidence. The currently inspected smoke script disables workers and simulates completion; that limitation is pending replacement in Sprint 5 and must not become a Sprint 6 requirement.

- `frontend/scripts/smoke-stabilization.mjs`: existing Puppeteer/local backend harness, to be extended from its final Sprint 5 successor.
- `backend/src/tests/application.test.ts`, `src/tests/matcher.test.ts`, `src/tests/ai-idempotency.test.ts`, `src/tests/stabilization-safety.test.ts`: focused/integration assertions.

- [Sprint 5 COM-40 draft](../sprint-5/COM-40.md), [review](../sprint-5/planning-review.md) and [runbook](../sprint-5/verification-runbook.md): required final fixture/worker/safety behavior.

## 5. Problem/gap

Unit tests alone do not expose UI cache races, mismatched contracts or worker/manual-state interaction. A fake completion smoke hides pipeline regressions; a blanket zero-AI assertion is wrong when the same run intentionally processes fixture email through real workers. Destructive migrations can also run before a Vitest guard unless the CLI path is explicitly guarded.

## 6. Proposed implementation

Extend the final Sprint 5 harness and retain its existing acceptance scenarios. Use real local routes, pg-boss queue, Gmail/email workers, AI operation ledger, matcher and database. Stub only external Google/Gemini boundaries with deterministic fixtures; block all unexpected outbound traffic in backend and browser. Disable real notification delivery. Do not add production test endpoints or mock-mode flags.

Use an exclusive disposable local smoke database containing only harness-owned fixture data. No parallel Vitest suite, arbitrary queued jobs or non-harness users may share it while workers run. Set test configuration before backend imports; NODE_ENV=test disables automatic worker startup, then explicitly register the required real Gmail/email workers. Use a properly encrypted fake token, fixture encryption key, valid history anchor, and an assertion that incremental history.list was actually called. Retain Sprint 5's small nonzero fixture AI budget through real runOperation and its exclusively owned daily ledger.

Seed initial fixtures, then prove sync 202 → real worker completion → persisted domain state → mounted browser update. Do not manually write completion/domain results after the trigger to satisfy the positive path. Include a target older than the first 20 applications and history beyond one page.

Verify a manual set, a later fixture email changing AI state while manual state/revision remain unchanged, a completed-operation replay without additional provider calls, and explicit clear revealing the persisted AI state. Exercise a two-session conflict even when a background refetch precedes the first save. Cover stale GET, lost acknowledgement, invalid success body, failed reconciliation, section retry and navigation. UI-level fault injection may hold/drop a transport response; it must not fabricate domain success.

Measure manual correction effects only after prior fixture jobs are drained, or with reliable operation-specific attribution. Assert zero provider calls, job enqueues and AI-ledger/event/action changes for that mutation. The overall smoke may legitimately use fixture AI calls. Completed-AI replay must use stored results and preserve event/action uniqueness; do not assert zero queue activity for replay when existing matcher behavior can enqueue notification work. Keep notification delivery disabled and account for those jobs in cleanup.

For fresh/upgrade migration checks, use separate guarded disposable lanes. Seed approximately 1,620 synthetic emails plus representative legacy statuses, timestamps, owners and completed AI operations before the upgrade. Compare IDs/fields/constraints and counts afterward. Synthetic volume is not the user's preserved original dataset; link Sprint 5's measured preservation evidence separately.

Teardown must follow final Sprint 5 ordering: stop request intake and worker fetch, drain or abort handlers and prove no future writes, retain fixture action IDs before user cascades, remove owner jobs plus notification jobs identified by action IDs, clean exclusively owned fixture budgets, then close queue/DB/server/browser resources. Do not restart workers merely to clean up. A failed drain leaves the isolated lane quarantined with diagnostics; do not race cleanup against live handlers.

## 7. Architecture impact

Exercise existing boundaries without adding runtime infrastructure. Verification must distinguish synthetic/local evidence, Sprint 5 live Gmail evidence and any separate provider/deployment gates. Keep all helpers within existing test/harness structure unless a small shared test helper is necessary.

## 8. Data model impact

Verify S6-02's additive revision migration, fresh default zero and unchanged legacy fields. No new schema in this ticket. Never reset the preserved mailbox database, delete AI operations for replay, or alter production ownership constraints for fixtures. The safety guard must run before every migration CLI lane.

## 9. API contracts

End-to-end validate create/list/detail/events/PATCH contracts, ownership and structured errors. Exercise real serialization/runtime parsing rather than only typed fixtures. Include required-field omissions and valid null distinctions in transport-level fault tests. Preserve 20-item pagination semantics and direct lookup of older applications.

## 10. Frontend impact

Test existing list/detail workflow in desktop and narrow viewport with keyboard navigation. Verify source labels, unknown values, pending/conflict/unknown-save states, independent section errors and no stale overwrite. Preserve final Sprint 5 bounded refresh after delayed AI processing without adding permanent polling.

## 11. AI impact

No new model/prompt/version or live-provider requirement for the manual feature. Fixture workers use the real operation ledger and budget; successful completed replay consumes no additional provider call. Manual correction consumes none. Do not bypass runOperation, set a zero budget that makes the positive pipeline impossible, or clear completed operation rows.

## 12. Background-job impact

Exercise real workers, claims and matching inherited from Sprint 5. Real notification delivery remains disabled; queued fixture notifications must be attributed and cleaned safely. Manual PATCH enqueues no job. Preserve final Sprint 5 retry/fencing tests and delayed browser-domain refresh scenarios.

## 13. Security/privacy

Only disposable synthetic data enters test artifacts. Explicitly validate expected local test target before CLI or harness setup, and verify database provenance/exclusivity in addition to its name. Block unexpected Google/Gemini/Discord/other network traffic. Redact URLs with credentials, cookies, tokens, user emails and raw payloads from logs/screenshots.

## 14. Testing

Run focused checks per ticket, then full backend/frontend tests, typecheck, lint and build once the implementation is stable. Run fresh schema and additive-upgrade checks in guarded separate lanes, followed by the exclusive real-worker browser smoke. Do not overlap DB-resetting Vitest with a worker harness. Verify both successful and failed-run teardown.

Link actual final Sprint 5 live incremental and repeat-sync evidence; local fixtures do not replace it. Live Gemini/Discord success is supplementary to Sprint 5's mandatory Gmail proof, with any independent stabilization deployment gates recorded separately. Record actual outcomes and commit IDs, never infer runtime success from this proposal.

## 15. Acceptance criteria

- [ ] Sprint 5 entry evidence and final integrated commit IDs are linked.
- [ ] Final Sprint 5 real-worker/refresh/pagination/safety scenarios remain intact.
- [ ] Set → later AI update → conflict → explicit clear works in API/database/browser.
- [ ] Frozen draft revision survives background refresh; stale saves are rejected.
- [ ] Stale reads, lost acknowledgements and malformed contracts recover without blind retries.
- [ ] Manual mutation makes zero provider calls, enqueues and AI-ledger/event/action changes, measured in an isolated interval.
- [ ] Completed-operation replay adds no provider call or duplicate event/action; fixture queue cleanup handles existing notification behavior.
- [ ] Guarded fresh/upgrade lanes preserve synthetic legacy IDs/choices/constraints; original-data preservation is linked separately.
- [ ] Unexpected outbound traffic is blocked; real workers stop before fixture cleanup.
- [ ] Full checks and desktop/mobile keyboard smoke pass with actual evidence.
- [ ] Operating docs describe implemented behavior, rollout/rollback and remaining limitations accurately.

## 16. Non-goals

## 18. Failure/recovery behavior

If target guard/provenance/exclusivity fails, stop before migration/setup. If unexpected outbound traffic is attempted, fail the run. If workers cannot drain, preserve the isolated lane for diagnosis and prevent further writes before cleanup. UI unknown-outcome and conflict behavior must remain recoverable without automatic mutation replay.

A failed check blocks completion; retain sanitized evidence and rerun the affected lane after correction. Do not manufacture success by editing domain results, disabling workers or deleting completed AI claims. Rollback retains additive schema and user choices with S6-01 canonical reads.

## 21. Engineering decision notes

Real workers plus deterministic external providers test the integration boundary without live account side effects. A nonzero isolated AI budget is necessary to prove the positive pipeline; zero-call assertions belong to manual operations and completed replay intervals. Separate DB lanes prevent one suite deleting another's fixtures. Synthetic migration preservation and real mailbox preservation are different evidence, both explicitly accounted for.
