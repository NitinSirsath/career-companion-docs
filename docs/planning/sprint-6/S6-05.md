## 5. Problem/gap

Unit tests alone do not expose UI cache races, mismatched contracts or worker/manual-state interaction. A fake completion smoke hides pipeline regressions; a blanket zero-AI assertion is wrong when the same run intentionally processes fixture email through real workers. Destructive migrations can also run before a Vitest guard unless the CLI path is explicitly guarded.

## 6. Scope and requirements

Extend the final Sprint 5 harness and retain its existing acceptance scenarios. Use real local routes, pg-boss queue, Gmail/email workers, AI operation ledger, matcher and database. Stub only external Google/Gemini boundaries with deterministic fixtures; block all unexpected outbound traffic in backend and browser. Disable real notification delivery. Do not add production test endpoints or mock-mode flags.

Use an exclusive disposable local smoke database containing only harness-owned fixture data. No parallel Vitest suite, arbitrary queued jobs or non-harness users may share it while workers run. Set test configuration before backend imports; NODE_ENV=test disables automatic worker startup, then explicitly register the required real Gmail/email workers. Use a properly encrypted fake token, fixture encryption key, valid history anchor, and an assertion that incremental history.list was actually called. Retain Sprint 5's small nonzero fixture AI budget through real runOperation and its exclusively owned daily ledger.

Seed initial fixtures, then prove sync 202 → real worker completion → persisted domain state → mounted browser update. Do not manually write completion/domain results after the trigger to satisfy the positive path. Include a target older than the first 20 applications and history beyond one page.

Verify a manual set, a later fixture email changing AI state while manual state/revision remain unchanged, a completed-operation replay without additional provider calls, and explicit clear revealing the persisted AI state. Exercise a two-session conflict even when a background refetch precedes the first save. Cover stale GET, lost acknowledgement, invalid success body, failed reconciliation, section retry and navigation. UI-level fault injection may hold/drop a transport response; it must not fabricate domain success.

Also exercise a real application POST that commits before its `201` response is corrupted or dropped. Verify S6-01 creation-response recovery retains the draft, refreshes owned reads and makes no blind second POST; failed reads and same-company/role records must not manufacture certainty or automatic deduplication.

Measure manual correction effects only after prior fixture jobs are drained, or with reliable operation-specific attribution. Assert zero provider calls, job enqueues and AI-ledger/event/action changes for that mutation. The overall smoke may legitimately use fixture AI calls. Completed-AI replay must use stored results and preserve event/action uniqueness; do not assert zero queue activity for replay when existing matcher behavior can enqueue notification work. Keep notification delivery disabled and account for those jobs in cleanup.

For fresh/upgrade migration checks, use separate guarded disposable lanes. Seed approximately 1,620 synthetic emails plus representative legacy statuses, timestamps, owners and completed AI operations before the upgrade. Compare IDs/fields/constraints and counts afterward. Synthetic volume is not the user's preserved original dataset; link Sprint 5's measured preservation evidence separately.

S6-05 must extend the Sprint 5 teardown to satisfy the shared runbook's required order: stop new browser/API activity, HTTP request intake and worker fetch; drain or abort active HTTP and worker handlers and prove no future writes; then clean fixture jobs, owners and exclusively owned budgets while database access remains available. Keep deterministic provider adapters and outbound blocking active until handlers are quiescent. Retain action IDs before owner cascades so notification jobs can be removed. Finally close remaining resources and release lane ownership. Do not preserve the current server-close-after-deletion order or restart workers merely to clean up. A failed drain leaves the isolated lane quarantined with diagnostics; do not race cleanup against live handlers.

## 7. Architectural constraints

Final architecture verification is a required deliverable, not a generic smoke pass. Review the final diff and record a pass/fail with evidence for each boundary:

- React/Query → existing API/services → Prisma/PostgreSQL and pg-boss remain the architecture; no new provider, queue, workflow service or infrastructure.
- S6-01 owns canonical status mapping and owner-scoped revision writes. AI changes only AI-owned fields; no manual write creates events/actions/jobs or paid work.
- S6-02 evidence is bounded, owner-checked and recording-ordered. No new occurrence chronology, backfill or raw-content exposure. D1 resolution is reflected in final action scope.
- S6-03 delivery behavior matches the installed queue configuration; callback success cannot hide unattempted delivered work. Email/application lock order, fresh state checks and domain uniqueness preserve manual decisions under tested interleavings.
- S6-04 uses synchronized runtime contracts, frozen drafts, cancellation and uncertain-save recovery while preserving Sprint 5 bounded refresh.
- Migration and rollback preserve additive revision data, ownership constraints, completed AI claims, user choices and recorded evidence. No business uniqueness constraint merges separate applications for the same company/role.

Exercise existing boundaries without adding runtime infrastructure. Verification must distinguish synthetic/local evidence, Sprint 5 live Gmail evidence and any separate provider/deployment gates. Keep all helpers within existing test/harness structure unless a small shared test helper is necessary.
