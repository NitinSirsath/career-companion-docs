## 1. Title

Establish application status semantics and manual user correction.

## 2. Objective

Give every API/UI surface one effective-status rule, and let users set, change and clear their own status without a competing editor silently overwriting a newer manual decision.

## 3. Context

UF-09 in [user flows](../../product/user-flows.md) requires manual correction. The [domain model](../../domain/domain-model.md) already separates AI and user state, but no mutation is exposed. Revision and clear semantics below are proposed decisions for approval, not previously delivered behavior.

## 4. Current implementation

- `backend/prisma/schema.prisma`: Application has aiStatus, userStatus and userStatusSetAt; no manual revision.
- `backend/src/services/application.ts`, `src/routes/application.ts`, `src/contracts/application.ts`: owned reads and creation, no status PATCH.
- `backend/src/services/matcher.ts`: locks email then application and updates AI state independently.
- `backend/src/tests/application.test.ts`, `src/tests/matcher.test.ts`, `src/tests/ai-idempotency.test.ts`, `src/tests/stabilization-safety.test.ts`: existing focused test locations.
- `backend/src/utils/testDatabase.ts`: safety helper; direct Prisma CLI does not invoke it.
- `frontend/scripts/sync-contracts.mjs` and application fixtures need coordinated updates. Its old sibling path currently skips synchronization in the migrated layout; follow the runbook prerequisite.
- `frontend/src/routes/applications.tsx` is AI-first while `applications.$id.tsx` is user-first; the list regression test asserts the incorrect precedence. No canonical derived response fields exist yet.

## 5. Problem/gap

List/detail precedence diverges from the domain user-first rule, and generic JSON typing cannot detect malformed deployed responses. There is no supported correction path. A naïve last-write-wins PATCH would lose concurrent edits; updatedAt is unsuitable as a manual token because AI/background work also changes the application.

## 6. Scope and requirements

### Canonical reads

Extend the existing backend application response mapper with three derived, required fields:

```ts
effectiveStatus: ApplicationStatus | null; // userStatus ?? aiStatus
statusSource: 'USER' | 'AI' | 'UNKNOWN';
hasStatusConflict: boolean; // both non-null and unequal
```

Use USER whenever userStatus is non-null, including when it equals AI. Use AI only when userStatus is null and aiStatus is non-null. Both null means UNKNOWN and no conflict. Preserve all existing response fields.

Add these required fields to the shared schema and sync it through the existing frontend script. Parse create/list/detail/PATCH responses in the relevant API methods with those schemas. Missing fields, invalid enums and inconsistent derived values must fail validation; do not add defaults that silently reconstruct an outdated response. A focused refinement can assert the precedence invariant. Keep unrelated API methods out of this refactor.

List and detail consume the canonical fields. Render a neutral unknown state for a valid null; do not default to APPLIED. Expose user/AI provenance consistently without redesigning the pages. An invalid read response shows a recoverable load error; S6-04 will keep editing disabled until a valid application is available. An invalid successful write response follows the endpoint-specific recovery rules below, not read-error retry behavior.

### Application creation response recovery

This ticket also owns the existing Add Application dialog's handling of the newly validated create response. POST creation can commit before a malformed `201`, lost response, timeout or 5xx reaches the client. Preserve the submitted draft, show “Creation outcome unknown,” and do not reset/close the dialog as success or offer an ordinary resubmit as though creation definitely failed. Disable automatic POST retry explicitly and block duplicate submission while the request or recovery is pending.

Reconcile by refreshing the owned, paginated application list and offering review of existing applications. Creation may provide no trustworthy application ID, so do not require the status-PATCH recovery path's known-ID GET. Validate recovery reads normally; a user-selected existing application can be inspected through its owned detail endpoint. Matching company/role or other submitted fields does not identify this POST, and absence from one page or an early refresh does not prove it failed or cannot still commit. Do not automatically select, merge or deduplicate records, add a business uniqueness constraint, or invent an idempotency API.

If the read fails, retain the draft and unknown-outcome message, keep normal submission blocked, and offer retry of the read. A successful refresh enables review, not automatic resubmission or a claim that a matching row proves which request created it. The user may leave creation to inspect an existing application. Any further POST after review must be a deliberate new creation with an explicit explanation that the earlier request may already have created an application; no automatic replay or exactly-once guarantee is implied. Definitive validation/auth rejection follows existing error handling and is distinct from an uncertain result.

### Manual correction

Add an owned service operation and `PATCH /api/applications/:id/status`. In one transaction, lock the application row using both id and authenticated userId, verify its manual revision, then apply a narrow change.

Compare `expectedUserStatusRevision` before testing for a no-op. A stale request returns 409 even if its requested value equals the latest value. With a current revision, identical userStatus returns 200 unchanged, preserving revision, confirmation timestamp and updatedAt. A changed non-null value sets userStatus, sets server-generated userStatusSetAt and increments revision once. Clearing a non-null override sets both userStatus and userStatusSetAt to null and increments revision once. Ordinary updatedAt changes on a real write.

Return the full canonical response, including the new revision, from the same transaction snapshot. Reuse a transaction-aware mapper/query for enrichment rather than performing an unrelated later read that obscures the acknowledged revision. Do not lock emails or perform external calls. Application-only locking must remain compatible with matcher's email-then-application order.

AI updates must never modify userStatus, userStatusSetAt or userStatusRevision. Manual corrections must not modify aiStatus, create recruitment events, resolve actions, enqueue jobs, invoke providers or alter AI operation/budget records. Follow the domain distinction between latest correction provenance and recruitment history.

## 7. Architectural constraints

Extend the current authenticated route/service/contract boundary. Database concurrency protects manual decisions across tabs/devices; frontend frozen revisions in S6-04 ensure that protection is actually used. No distributed lock, outbox or new worker.

## 8. Data model impact

The three canonical status fields (effectiveStatus, statusSource, hasStatusConflict) are derived response values, not persisted columns. Only userStatusRevision is added to storage.

Propose `Application.userStatusRevision Int @default(0)` with a new additive migration under the existing `backend/prisma/migrations/` directory. No migration file is created by this planning task. Existing rows receive zero; preserve stored statuses and timestamps exactly. A legacy non-null userStatus with null userStatusSetAt remains “confirmation time unknown”; do not invent dates.

No new table/index is needed for primary-key row locking. Fresh and upgrade tests must retain IDs, ownership constraints, existing AI operations, events and actions. Use the guard before any migration command, and regenerate Prisma before typecheck/build. Preserve data on rollback; no reset or destructive down migration.

## 9. API contracts

POST create (201), GET list/detail (200), and PATCH (200) use the same mapper and required canonical fields/revision. Preserve authenticated reads, 20-item pagination and owned direct detail. S6-02 later enriches recentEvent through this same mapper, including PATCH responses. Backend additions deploy before the client requires them; a new client against an old backend must show a contract error, never masking defaults.

Strict request body, rejecting unknown fields:

```json
{
  "userStatus": "INTERVIEW",
  "expectedUserStatusRevision": 0
}
```

userStatus accepts APPLIED, RECRUITER_CONTACT, ASSESSMENT, INTERVIEW, OFFER, REJECTED, CLOSED or null. Revision is a nonnegative integer. Validate the path as UUID. Reject submitted userId, aiStatus, server timestamps and other undeclared fields.

Success 200 returns the full canonical ApplicationResponse; add required `userStatusRevision` to create/list/detail/mutation schemas. New applications return zero; the response revision is a required nonnegative integer with no default masking a missing key. Coordinate frontend fixtures and runtime parsing immediately.

| HTTP | Error code / meaning |
| --- | --- |
| 400 | VALIDATION_ERROR: invalid UUID/body/status/revision |
| 401 | UNAUTHORIZED: no valid session |
| 404 | NOT_FOUND: missing or foreign application, identical response |
| 409 | STATUS_CONFLICT: stale expected manual revision; refetch before deliberate retry |
| 500 | Sanitized existing internal-error envelope; client must consider the outcome uncertain |

Use the project's existing error envelope. A conflict need not disclose a snapshot in its body; the owned GET supplies current state. No automatic mutation retry.

## 10. Frontend impact

This ticket owns canonical list/detail display, affected API runtime parsing, synchronized revision schemas/fixtures, and creation-response recovery in the existing Add Application dialog. S6-04 supplies the status editor and status-mutation recovery. Preserve useful cached data with an explicit refresh failure; sanitize contract errors without exposing raw application/email payloads. The status client must submit the revision captured when editing began; a background refetch must not replace that draft's revision. Missing revision blocks editing rather than defaulting to zero.

## 11. AI impact

None on provider abstraction, prompts, schemas, operation versions, budgets or retries. Existing aiStatus is retained even during a manual override; clearing reveals its current persisted value without a new AI call.

## 12. Background-job impact

Reads and correction enqueue no work; reads persist no changes. Test zero job enqueue operations, including notifications. Concurrent legitimate AI processing can proceed but must preserve all three manual fields. Drain unrelated fixture work before measuring correction side effects.

## 13. Security/privacy

Authenticate before selecting a row; scope the lock/write by owner. Never trust a body userId. Foreign and missing IDs use the same 404. Preserve existing credential/cookie protections and DB ownership triggers. Logs may contain approved correlation IDs and sanitized errors, not email content or credentials.

## 14. Verification expectations

Table-test all 64 combinations of the seven statuses plus null for both fields. Assert effective status, source and conflict. Verify create/list/detail agree and foreign detail remains inaccessible. Correct the frontend AI-first regression test and cover valid unknown, user-equals-AI, conflict, missing required fields, malformed values and recoverable load failure.

Schema parsing must actually execute in API tests; TypeScript fixtures alone cannot detect an outdated deployed backend. Preserve pagination/direct-detail regression coverage.

For creation, persist a real fixture application, then corrupt/drop its `201` response. Verify that the dialog retains its draft, enters unknown-outcome recovery, refreshes the owned list and sends no second POST automatically or through an ordinary retry click. Cover failed reconciliation, missing/unusable response ID, an existing application with identical company/role, and a first-page/early refresh that cannot establish the outcome. A fresh list must not auto-match or silently re-enable submission. Verify explicit review before any deliberate new creation and distinguish definitive validation rejection from uncertain writes.

Cover all statuses, clear, repeated clear, same-value no-op, legacy null timestamp, strict payload validation and ownership. Two competing real changes with the same revision must yield one successful change and one 409; repeated current no-ops stay unchanged. Assert revision comparison precedes no-op detection. Interleave AI writes with manual set/clear and verify separation.

Simulate lost acknowledgement after a changed commit: retrying the original stale revision returns 409 without another change. Verify rollback on transaction failure. Snapshot event/action/job/AI-ledger counts around a quiescent correction to prove no side effects. Test fresh schema and additive upgrade using synthetic legacy rows; compare fields before/after. Guard rejection must precede any migration invocation.

## 15. Acceptance criteria

- [ ] All 64 AI/user status combinations obey canonical precedence/source/conflict on API and UI.
- [ ] Create/list/detail/PATCH carry the same required fields and are runtime-validated without masking defaults.
- [ ] A committed create with malformed/lost success response preserves its draft and reconciles through owned reads without blind POST replay or automatic deduplication; failed recovery remains visibly uncertain.
- [ ] Corrected list/detail display retains true unknown, paging, direct lookup and recoverable load errors.
- [ ] Owned set/change/clear works with the seven supported statuses and null.
- [ ] Concurrent edits use an atomic lock/revision check; stale requests always return 409.
- [ ] Current same-value requests preserve revision and timestamp; changes increment revision exactly once.
- [ ] AI writes preserve all manual fields and revision.
- [ ] Strict payload validation and identical foreign/missing 404 are tested.
- [ ] Correction makes zero provider calls, job enqueues, AI-ledger changes, events or action transitions.
- [ ] Required revision appears in every application response and synchronized fixture.
- [ ] Guarded fresh/upgrade checks preserve existing data and ownership constraints.
- [ ] Lost-response, rollback and legacy-timestamp behavior are documented and tested.

## 18. Failure/recovery behavior

For the status PATCH, validation/auth/ownership/conflict rejection does not mutate. Transaction failure rolls back. A timeout, lost response or malformed 2xx can occur after commit: refetch the owned application and preserve the draft; never automatically resend with a fresh revision. If reconciliation fails, show “Save outcome unknown” and block save until current state is loaded. A 409 requires explicit user review and deliberate rebasing before another save.

For POST creation, follow section 6's creation-response recovery: the application ID may be unavailable, there is no expected revision protecting a repeat POST, and a list refresh does not by itself prove the request's outcome. Retain the draft, explain uncertainty, reconcile owned reads and require deliberate review before any new creation.

Roll back UI capability by disabling editing while retaining canonical S6-01 reads and persisted corrections. Keep the additive column. Do not undo user decisions or restore AI-first display.

S6-05 owns final integrated acceptance. Derived status avoids a second persisted truth; runtime parsing detects deployed contract mismatch.
