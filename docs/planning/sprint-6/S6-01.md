## 1. Title

Unify effective application status across API and UI.

## 2. Sprint goal contribution

Give every application surface the same answer to “what is my current status?” before adding a correction workflow.

## 3. Context

The [domain model](../../domain/domain-model.md) defines effective status as `userStatus ?? aiStatus`. Both fields already exist. The current list reverses that precedence, while detail follows it. This is a demonstrated inconsistency, not a new inference policy.

## 4. Current implementation

Repository prefixes and inspected commit IDs are in the [architecture review](architecture-review.md).

- `backend/src/services/application.ts`: shared private response mapper used by create/list/detail, but no canonical effective-status fields.
- `backend/src/contracts/application.ts`: nullable AI/user status fields and seven-value enum.
- `backend/src/routes/application.ts`: POST create, GET list/detail/events/actions.
- `frontend/src/routes/applications.tsx`: AI-first display; `frontend/src/routes/applications.$id.tsx`: user-first display.
- `frontend/src/api/client.ts`: generic typed JSON currently casts without runtime schema validation.
- `frontend/src/tests/applications.test.tsx`: explicitly asserts AI precedence; update that assertion.

## 5. Problem/gap

A user-confirmed status can appear differently in the list and detail. Client-side fallback can also disguise an old or malformed API response as a genuine unknown status.

## 6. Proposed implementation

Extend the existing backend application response mapper with three derived, required fields:

```ts
effectiveStatus: ApplicationStatus | null; // userStatus ?? aiStatus
statusSource: 'USER' | 'AI' | 'UNKNOWN';
hasStatusConflict: boolean; // both non-null and unequal
```

Use USER whenever userStatus is non-null, including when it equals AI. Use AI only when userStatus is null and aiStatus is non-null. Both null means UNKNOWN and no conflict. Preserve all existing response fields.

Add these required fields to the shared schema and sync it through the existing frontend script. Parse create/list/detail responses in the relevant API methods with those schemas. Missing fields, invalid enums and inconsistent derived values must fail validation; do not add defaults that silently reconstruct an outdated response. A focused refinement can assert the precedence invariant. Keep unrelated API methods out of this refactor.

List and detail consume the canonical fields. Render a neutral unknown state for a valid null; do not default to APPLIED. Expose user/AI provenance consistently without redesigning the pages. A contract error shows a recoverable load error; S6-04 will keep editing disabled until a valid application is available.

## 7. Architecture impact

Centralize the read rule in the existing ApplicationService boundary. Shared contracts remain backend-authored and frontend-synchronized. No new service, provider, state machine, or infrastructure is needed.

## 8. Data model impact

None. The three fields are derived response values, not persisted columns. No migration, backfill, historical replay, or modification of either stored status.

## 9. API contracts

The new required fields appear identically in `POST /api/applications` (201), `GET /api/applications` (200 paginated), and `GET /api/applications/:id` (200). Existing authentication, pagination, owned detail 404, and validation errors remain intact.

Deploy backend additions before the frontend starts requiring them. Old clients ignore additive fields; a new client against an old backend reports a contract mismatch. S6-02 subsequently adds the required revision and S6-03 extends history; coordinate fixtures at each step. No new endpoint in this ticket.

## 10. Frontend impact

Update both routes and their API methods. Maintain independent loading, empty and failure behavior. Keep valid cached data distinguishable from a failed refresh; never show a fabricated status as a successful load. Sanitize schema-error messages instead of logging raw application/email payloads.

## 11. AI impact

No Gemini calls, prompt/schema version changes, retries or operation resets. AI still writes only its existing fields. Disagreement with a manual status is informational and does not trigger reclassification.

## 12. Background-job impact

None. Reads must not enqueue sync, processing, matching or notification jobs. Retain Sprint 5 refresh behavior; this ticket does not add polling.

## 13. Security/privacy

Keep owner filters and existing auth on every endpoint. Derived fields disclose only already-owned application state. Do not add email bodies, tokens, model prompts or cross-user counts to responses or error logs.

## 14. Testing

Table-test all 64 combinations of the seven statuses plus null for both fields. Assert effective status, source and conflict. Verify create/list/detail agree and foreign detail remains inaccessible. Correct the frontend AI-first regression test and cover valid unknown, user-equals-AI, conflict, missing required fields, malformed values and recoverable load failure.

Schema parsing must actually execute in API tests; TypeScript fixtures alone cannot detect an outdated deployed backend. Preserve pagination/direct-detail regression coverage.

## 15. Acceptance criteria

- [ ] All 64 combinations obey user-first precedence and correct source/conflict semantics.
- [ ] Create/list/detail return the same required canonical fields.
- [ ] List/detail render matching statuses, including true unknown.
- [ ] API methods validate responses at runtime; missing/malformed/inconsistent fields cause a recoverable contract error.
- [ ] Ownership, 20-item pagination and direct-detail behavior remain covered.
- [ ] No persisted data, AI operations, jobs or provider calls change.
- [ ] Focused checks pass and synchronized contracts contain no unrelated drift.

## 16. Non-goals

Manual mutation/editor, revision migration, history metadata, inference changes, search/filter, dashboard redesign and broad API-client replacement.

## 17. Dependencies

The full [Sprint 5 entry gate](README.md#b-why-this-sprint-follows-sprint-5) applies. Reconcile the final stabilization/Sprint 5 source before implementing. This ticket precedes S6-02/03/04; ensure later contract additions also update fixtures and validation. Local IDs are not Linear issues.

## 18. Failure/recovery behavior

Network/auth/API errors follow existing handling. Invalid successful responses fail closed as contract errors, not UNKNOWN. Retrying a read is safe. An additive backend rollout can precede the client; roll back display changes only while retaining correct user-first precedence. Never roll back to the known AI-first rule.

## 21. Engineering decision notes

Derived response fields avoid duplicated precedence rules and a second persisted source of truth. Validating affected API methods addresses the actual mismatch risk without a generic client rewrite. Status disagreement does not prove either value is wrong. Retain the manual choice and expose provenance.
