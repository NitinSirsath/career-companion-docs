## 1. Title

Deliver the application status correction and evidence-review workflow.

## 2. Sprint goal contribution

Make correctable status and understandable source history usable together, including competing edits and uncertain network outcomes.

## 3. Context

The [UF-07/UF-09 flows](../../product/user-flows.md) require inspection and manual correction. S6-01 supplies canonical reads, S6-02 protected writes, and S6-03 bounded source metadata. This ticket joins those contracts into the existing detail/list UI.

## 4. Current implementation

- `frontend/src/routes/applications.$id.tsx`: direct detail, events and actions queries; combined error handling can hide otherwise valid sections.
- `frontend/src/routes/applications.tsx`: paginated application list.
- `frontend/src/api/client.ts`: typed fetch, currently no application-query AbortSignal parameter or preserved structured error code.
- `frontend/src/contracts/application.ts`: synchronized from backend; do not independently fork its definitions.
- `frontend/src/tests/applications.test.tsx`, `src/tests/stabilization-ui.test.tsx`: existing tests to extend.
- `frontend/src/components/ui/`: existing button/badge/input/label primitives; inspect final contents before adding a primitive. A select wrapper is proposed only if needed, not claimed to exist today.

Existing query families include `['application', id]`, `['applications', params]`, `['application-events', id, offset]` and application actions. Reconcile the exact final keys and refresh lifecycle with Sprint 5 before changing them.

## 5. Problem/gap

A normal mutation form can silently adopt a newer revision during background refresh, defeating conflict detection. Uncancelled reads can repaint old state after save. Timeouts or invalid success bodies can leave users unsure whether a correction persisted. Current generic response typing does not detect that mismatch at runtime.

## 6. Proposed implementation

Add an inline status editor to the detail header using existing design primitives. Offer all seven statuses and “Use AI status” to clear the override. Explain that clearing uses the latest persisted AI result (possibly unknown), does not rerun AI, and that status changes do not complete actions or send notifications. Show effective status/source, optional AI disagreement, and user confirmation time when known. A legacy missing time stays unknown.

### Draft and conflict behavior

Opening the editor captures `{ applicationId, userStatusRevision, originalUserStatus, draftUserStatus }`. The captured revision and target remain frozen for that editing session. Background reads may update the visible current server state, but never reset the draft or replace its base revision. Show that newer state is available where useful.

Save submits the frozen revision and target. Disable duplicate submission while pending and set mutation retry to false explicitly. On 409, preserve the draft, refresh current state, and ask the user to compare it with their intended correction. Only an explicit review/rebase action may capture a new revision; do not resubmit automatically. Cancelling/reopening can intentionally start a new session. Test a second device saving and a background refetch completing before the first device clicks Save: the first stale save must still get 409.

### Request, cache and uncertain-outcome behavior

Extend affected API methods to accept AbortSignal and propagate TanStack Query cancellation through fetch. Await cancellation of outstanding detail/list reads before PATCH. Cancel any reads restarted during the mutation before applying its result. Keep the response target captured in mutation variables; route changes must never apply the result to another application.

Parse mutation/create/detail/list/event responses with synchronized schemas as defined by S6-01/03. Preserve HTTP status and machine-readable error code in the API error abstraction so 409 can be handled reliably. Required fields have no compatibility defaults. Use sanitized contract-error messages.

On validated success, update the original detail and any matching list item from the canonical response, refusing to replace a cached higher userStatusRevision with a lower one. Invalidate/refetch affected detail/list queries to reconcile concurrent AI changes and other enrichment. Respect cancellation for earlier read promises so a delayed pre-save GET cannot overwrite an acknowledged correction. Manual revision orders manual state only; do not use it to suppress all AI refreshes. In-flight newer reads and normal Sprint 5 refresh must still work.

Use a bounded mutation request deadline (proposed 15 seconds, reconciled with any final Sprint 5 request utility). Aborting the client does not prove the server rolled back. Network failure, timeout, 5xx and malformed 2xx response are uncertain outcomes: refetch the owned application without automatic PATCH retry. A successful reconciliation shows current state and asks for review; matching the desired value does not prove which request wrote it. If reconciliation fails, retain the draft and show “Save outcome unknown”; disable Save until current state is loaded. Offer retry of the read, not a blind write using a fresh revision.

### Evidence and section states

Render history in recording order with separate “Recorded” and “Email date” labels. Show escaped subject/sender metadata when available; use a clear unavailable-source state otherwise. Label existing generated provenance/description as AI interpretation. For processing events, state changes describe AI status only; do not show an old→new arrow when values are equal or imply a change to the user's effective status.

Application, history and actions have independent loading/empty/error/retry states. A history/action failure must not block editing an otherwise valid owned application. A missing/malformed application contract does block editing. Retained cached data after a refresh failure must be visibly stale, not represented as a fresh confirmation. Reset editor state when navigating to a different application; keep any completed response scoped to its original cache key.

## 7. Architecture impact

Extend existing React/TanStack Query routes and focused client methods. Reuse Sprint 5's bounded refresh/cancellation work. No global state framework, broad component rewrite, permanent polling or new test infrastructure.

## 8. Data model impact

None beyond consuming S6-02's revision. No localStorage draft or persisted client override is introduced. The server remains authoritative; the in-memory draft is an explicitly unsaved user choice.

## 9. API contracts

Consume S6-01 create/list/detail canonical fields, S6-02 PATCH with expectedUserStatusRevision and full response, and S6-03 history/recentEvent fields. Runtime-parse every affected successful response. Distinguish genuine nullable values from missing keys. Handle structured 400/401/404/409 and sanitized unexpected errors; preserve session-expiry behavior.

No extra endpoint. Status PATCH must not call Gmail sync or inference. GET retries may be bounded; PATCH retry remains disabled.

## 10. Frontend impact

The list/detail share status presentation; the editor is detail-only. Use current spacing, typography, themes and primitives from [DESIGN_SYSTEM](../../DESIGN_SYSTEM.md). Provide labels, keyboard navigation, visible focus, pending and error announcements, and sensible focus return when closing the editor. Preserve narrow-screen usability and pagination. Avoid an unrelated card/layout redesign.

## 11. AI impact

No AI calls or changes. AI disagreement is context, not a warning that automatically alters user state. “Use AI status” clears persisted user override and never requests re-extraction.

## 12. Background-job impact

None from editing/history reads. Retain Sprint 5's mounted-page refresh after delayed domain processing. Explicitly test that background refresh cannot rebase an open editor. Do not disable legitimate workers to make UI tests pass.

## 13. Security/privacy

Render email metadata and generated text as escaped text, not HTML. Do not expose raw payloads in error messages, external links, logs or telemetry. Capture application ID at mutation start and keep cache writes scoped to that owned resource across navigation. Existing authenticated credentials and owner checks remain in force.

## 14. Testing

Extend API/component tests for success, set/change/clear, true unknown, legacy null confirmation time, pending duplicate clicks and section-level failures. Add deterministic deferred-response tests for:

- second-device save followed by background refresh before the stale editor's first save;
- 409 preserving draft and requiring explicit rebase;
- pre-save delayed detail/list GET resolving after acknowledgement;
- a request restarted during the mutation;
- a cached higher revision refusing a lower mutation response;
- lost acknowledgement, 5xx, timeout, invalid 2xx body and failed reconciliation;
- navigation while PATCH is pending;
- missing required fields versus valid null; malformed history isolated to its section.

Verify retry=false and propagated abort signals rather than only checking a final render. Cover source labels, escaped content, no false unchanged transition, >20 records, keyboard/mobile and Sprint 5 delayed processing refresh. Use existing Vitest/Testing Library and the final smoke harness for integrated scenarios.

## 15. Acceptance criteria

- [ ] Users can set/change/clear with correct source, timestamp and side-effect explanations.
- [ ] Draft target/revision stay frozen through background refresh; competing edits yield 409.
- [ ] Conflict recovery preserves the draft and requires deliberate review/rebase.
- [ ] Pending requests cannot duplicate save; automatic mutation retry is disabled.
- [ ] Stale reads cannot overwrite an acknowledged correction; cancellation reaches fetch.
- [ ] Unknown outcomes reconcile by reading; failed reconciliation preserves draft and blocks blind save.
- [ ] Runtime validation rejects missing/malformed contracts without converting them to unknown/empty.
- [ ] Navigation cannot apply a mutation to the wrong application.
- [ ] History/email/recording labels are honest, escaped, and independently recoverable.
- [ ] Existing pagination, Sprint 5 refresh, mobile, keyboard and theme behavior remain usable.

## 16. Non-goals

App-wide redesign, optimistic persistence, offline edits, localStorage drafts, full manual edit history, AI reruns, agenda/search/filter features, action completion automation and new UI frameworks.

## 17. Dependencies

The [Sprint 5 entry gate](README.md#b-why-this-sprint-follows-sprint-5) and S6-01/02/03 contracts must be complete. Preserve final Sprint 5 refresh/cancellation behavior and tests. Coordinate source/schema changes through backend-authored contracts, not a separate frontend definition.

## 18. Failure/recovery behavior

400 retains editable draft with a validation message; 401 follows auth recovery; 404 makes the resource unavailable. 409 retains draft and enters explicit conflict review. Network/timeout/5xx/invalid success response enters uncertain-save reconciliation. If that read fails, “Save outcome unknown” remains visible and Save stays disabled. No recovery path automatically replays PATCH with a newer revision.

Independent event/action failures remain local to those sections. Rollback may disable editor affordances while retaining correct S6-01 display and stored corrections. Refreshing or cancelling a draft never deletes server decisions.

## 21. Engineering decision notes

A frozen revision represents the state the user actually edited. Automatically refreshing it defeats optimistic concurrency. Server-confirmed updates plus cancellation/reconciliation avoid optimistic UI claiming a write that may have failed. Manual revision cannot order AI changes, so normal refetch remains necessary. Independent section errors preserve useful work without hiding data uncertainty.
