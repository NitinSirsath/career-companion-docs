## 1. Title

Expose owned source evidence and recording semantics in application history.

## 2. Sprint goal contribution

Let the user see which email supports recorded activity and distinguish recording time from email date or an actual recruitment-event time.

## 3. Context

Existing history records processing events, not a reconstructed recruitment chronology. The response contains an email ID without usable source metadata. UF-07 and the [domain history model](../../domain/domain-model.md) need an honest, explainable presentation before an agenda is considered.

## 4. Current implementation

- `backend/src/services/application.ts`: owned event query ordered by createdAt ASC then id ASC; list/detail recentEvent selects only type/createdAt.
- `backend/src/contracts/application.ts`: ApplicationEventResponseSchema, RecentEventSchema and a type-only paginated event response.
- `backend/prisma/schema.prisma`: existing email relation and stored metadata; no reliable occurredAt for this purpose.
- `backend/src/services/matcher.ts`: event oldState/newState describe AI state; event uniqueness protects replay.
- `backend/src/routes/application.ts`: paginated events route, 403 for both absent and foreign parent.
- `frontend/src/api/client.ts`, synchronized contracts and application tests consume these responses.

## 5. Problem/gap

Generic timestamps and transition arrows can imply that processing order is real-world order, or that an AI transition changed a user-confirmed effective status. Reading email metadata must also preserve ownership/minimization guarantees.

## 6. Proposed implementation

Extend both event and recent-event schemas with required recording/source fields:

```ts
recordedAt: string; // ISO timestamp, same instant as existing createdAt
sourceEmail: {
  id: string;
  subject: string | null;
  sender: string | null;
  receivedAt: string | null; // ISO timestamp when available
} | null;
```

Select only this metadata and the internal owner field needed to enforce ownership. Use bounded relation selection for the current event page and at most one recent event per application; avoid a per-event unbounded query pattern. Serialize new timestamps explicitly to ISO strings. Keep existing fields for compatibility.

Check the source belongs to the requesting owner as well as checking the parent. Missing/unavailable source returns null without failing an otherwise valid history page. If inconsistent legacy data references a foreign source, omit both sourceEmail and its exposing emailId from the response and emit only a sanitized integrity diagnostic. Never fetch the mailbox to repair it during a read.

Add an exported paginated event response schema using the existing pagination helper and use it for runtime parsing in the affected frontend API method. Extend application response parsing to validate enriched recentEvent. Missing required keys are contract errors; explicit null source is valid. Coordinate fixtures even before S6-04's richer UI lands.

## 7. Architecture impact

Read-only enrichment inside ApplicationService and synchronized contracts. No external provider request, new endpoint, timeline reconstruction service or new model inference. Continue recording-order pagination with deterministic ties.

## 8. Data model impact

None. Reuse stored email metadata and event createdAt. No migration, index, backfill, replay or fabricated occurrence timestamp. Older email dates may originate from a Date header; the UI label is “Email date,” not a guarantee of Gmail arrival time.

## 9. API contracts

`GET /api/applications/:id/events` keeps pagination and existing response fields and adds recordedAt/sourceEmail per item. `GET /api/applications`, detail, and the shared full application response extend non-null recentEvent with the same fields. A null recentEvent remains null; create normally has none. Ensure S6-02's mutation response uses the updated mapper as well.

Auth/validation behavior remains unchanged. Preserve events' existing 403 for missing or foreign parent; this ticket does not harmonize unrelated endpoint error policies. A null source is an available event with unavailable evidence, not an authorization bypass. New schema fields are required; deploy backend additions before requiring them in the frontend.

## 10. Frontend impact

S6-04 renders source metadata, “Recorded” time, and separate “Email date.” Existing createdAt remains for compatibility. AI provenance/description is labeled as AI interpretation, not verified source text. For AI processing events, old/new states describe AI only; unchanged values should not render a misleading transition arrow. No Gmail deep link is invented from an internal ID.

## 11. AI impact

No prompt/schema/provider/version/budget changes. Existing provenance may help inspection but is not a verified explanation. Completed AI operations remain reusable; evidence reads must not invoke reprocessing.

## 12. Background-job impact

None. History GET and metadata selection do not enqueue jobs. Matcher continues its existing event creation behavior. Manual corrections from S6-02 do not become recruitment events.

## 13. Security/privacy

Parent and source ownership both apply. Do not return stored user IDs, OAuth tokens, raw bodies, snippets, full extraction objects or model prompts. Render subject/sender as text in S6-04. Test that a foreign source cannot leak even its identifier through legacy inconsistent associations.

## 14. Testing

Cover owned source, null source, nullable metadata and ISO recording/email dates. Test distinct timestamps, equal-createdAt ties, a page with more than 20 events, empty history and recent-event selection. Verify foreign/missing parent behavior and mapper handling of inconsistent source ownership without disabling production DB constraints to manufacture a valid cross-owner link.

Use a focused mapper/mock fixture for the impossible-under-current-triggers legacy case, and integration tests for actual ownership constraints. Assert bounded selection and zero external calls. Runtime frontend parsing must reject missing new fields/invalid timestamps while accepting explicit nulls.

## 15. Acceptance criteria

- [ ] Events and recentEvent expose only owned, bounded source metadata.
- [ ] recordedAt matches createdAt; email date remains distinct and may be null.
- [ ] Ordering/pagination retain createdAt/id recording semantics and the 20-item cap.
- [ ] Missing source is explicit null; foreign source identifiers/content are not disclosed.
- [ ] No raw body, tokens, full AI payload or provider call is introduced.
- [ ] Required response schemas are exported, synchronized and parsed at runtime.
- [ ] Existing event/state fields and replay uniqueness are preserved without backfill.
- [ ] Relevant API/ownership/pagination/contract tests pass.

## 16. Non-goals

True occurredAt reconstruction, scheduled interview dates, normalized deadlines, agenda, raw email viewing, Gmail deep links, model reasoning generation, event-sourcing migration and manual edit audit history.

## 17. Dependencies

The [Sprint 5 entry gate](README.md#b-why-this-sprint-follows-sprint-5) and S6-01 apply. May proceed alongside S6-02 after agreeing the shared schema/mapper shape; coordinate any overlapping edits. S6-04 requires both backend contracts.

## 18. Failure/recovery behavior

Unavailable source metadata does not suppress a valid event. Failed history requests produce a section-level retry in S6-04 and do not disable a valid status editor. Invalid contracts remain recoverable errors rather than false empty history. Do not repair history by deleting rows, rerunning AI or resetting operations.

## 21. Engineering decision notes

An alias recordedAt clarifies existing meaning without rewriting historical data. Email date supplies context, not a claim about event occurrence. Keeping the existing sort avoids unstable invented chronology. Minimal metadata is sufficient for this sprint's evidence review; rich content and full temporal modeling require separate product/privacy decisions.
