## 1. Title

Verify and harden AI worker delivery and application matching concurrency.

## 2. Objective

Account for every delivered email-processing job and preserve owned domain effects and user decisions under concurrent processing. Change code only where verified behavior or an explicit delivery invariant requires it.

## 3. Context

The shortened ticket requires all delivered jobs to be processed and simultaneous-email matching to be reviewed. Its claim that `jobs[0]` causes massive silent loss is unsupported under the installed single-job configuration. Correcting that diagnosis does not remove the reliability goal.

## 4. Current implementation

Confirmed by source inspection on 2026-09-27, not a new runtime reproduction:

- `backend/src/jobs/emailProcessingJob.ts` registers with `{ includeMetadata: true }`, reads `jobs[0]`, and uses Sprint 5 completion, retry/failure and sanitized diagnostic handling.
- Installed pg-boss is 12.31.0. `node_modules/pg-boss/dist/manager.js` defaults `batchSize = 1` and `localConcurrency = 1`. Neither `src/services/queue.ts` nor this registration overrides batch size. Batch size and concurrency across worker registrations/processes are different controls.
- The installed manager normally completes delivered job IDs when the callback resolves and routes thrown failures through queue failure handling. Changing batch size requires verifying acknowledgment/error semantics, not merely adding a loop.
- `backend/src/services/matcher.ts` selects candidates before `applyMatch`, then locks email followed by owned application, rereads state and uses domain uniqueness constraints. Several paths already protect user-confirmed decisions.
- `src/tests/stabilization-safety.test.ts` covers duplicate concurrent effects and confirmed ignore replay; matcher tests cover existing decisions. These do not prove every distinct-email or resolution race.

## 5. Problem/gap

Suspected risks: future delivery changes could make first-element handling incomplete; pre-lock candidate reads and concurrent distinct emails may expose untested interleavings. Neither is a confirmed current batch-loss incident. Existing locks alone prove neither safety nor failure for every path.

Sprint 5 separately records final-attempt hard-kill/PROCESSING recovery as an operator limitation. Preserve it; do not silently promise a new failed-queue reconciliation consumer or exactly-once external delivery.

## 6. Scope and requirements

### Worker delivery

1. Record installed version, registration options, effective batch size and concurrency in each lane.
2. Preserve non-batched behavior unless verification justifies change. The existing ticket permits explicit single-job delivery or processing every delivered job. Make the chosen invariant explicit and test it; increased throughput is not a requirement.
3. Each delivered job needs an attempted, attributable outcome: completed, already-completed/unavailable skip, retry scheduled, or recorded terminal/exhausted failure under existing semantics. Queue acknowledgment is not proof of AI/domain completion.
4. Prove multiple queued distinct emails are all accounted for through actual queue/worker delivery. A failure must not silently acknowledge unrelated unprocessed work. If supporting batches larger than one, test mixed success/failure and array acknowledgment behavior before enabling them. If enforcing size one, test registration/delivery and prevent silent success for unexpected extra jobs.
5. Preserve Sprint 5 retry ceilings/backoff, owner scoping, diagnostic metadata, completion checks, operation claims, budgets and unknown-outcome holds. No paid-claim reset or operation-version change to make retries pass.

### Matching concurrency

Verify existing matching rules with controlled interleavings:

- Two distinct emails for the same owned application retain both legitimate per-email events/actions, valid existing AI transitions and all manual status fields. Serialize updates without losing one email's effects.
- Duplicate processing of one email preserves event/action uniqueness and completed AI results.
- Fresh match-state/ownership checks at the write boundary prevent stale automated selection from overwriting an accepted user link or ignore. Cover candidate-read-before-lock and ambiguous-branch updates, not only `applyMatch` in isolation.
- Competing legal user resolutions must not move existing effects between applications or overwrite an already accepted decision. Cover link-versus-link and link-versus-ignore while retaining current invalid-state/conflict behavior.
- Preserve deliberate ambiguity when several existing applications match company/role. Do not create, merge or impose business uniqueness on applications to solve concurrency.
- Keep email-then-application locking compatible with S6-01's application-only lock. Concurrent AI work preserves userStatus, userStatusSetAt and userStatusRevision during manual set/clear.

A correction that would change match selection policy, AI ranking, rematching permission or another product rule needs an explicit decision before dependent work. No such policy change is authorized by this ticket.
